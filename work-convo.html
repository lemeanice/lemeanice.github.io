Conversational Notification Admin

Setting up a notification internally today means a separate admin UI and integration for every channel. I'm the sole PM on a small AI-native squad rebuilding that as a single chatbot, where each channel becomes a "skill" the assistant runs instead of another tool to build and maintain. This is an internal, in-progress 0→1 project, so everything here is kept high level.

My roleSole PM, part-time (only non-eng role)
Team2-person AI-native squad (PM + 1 engineer)
ScopeInternal notification tooling, 0→1
StatusIn build & internal testing · not launched
The thesis
One assistant that learns channels, instead of one tool per channel

The existing notification admin is really many admin tools stitched together, roughly one bespoke UI and API set per notification channel. Every new channel carries a real cost: more interface to build, more backend to wire up, more surface area to maintain forever.

The bet behind this project is that a conversational interface collapses that cost. Instead of shipping a new screen for each channel, the assistant learns a new notification type as a skill that reuses a shared core. The marginal cost of the next channel drops toward the cost of teaching the assistant how that channel works. Because it's a first-of-its-kind build for the team, I'm framing it as pioneering, early-stage work rather than a results story: there are no launch metrics to cite yet.

Product & architecture
The skill-based model
Defined the skill-based approach that makes a new channel mostly configuration rather than net-new code, and the shared validation every skill inherits so no channel can quietly produce a bad task. This is the whole efficiency thesis, so getting the boundary of a "skill" right matters.
Safety ✦ Human / AI boundary
What the bot may never guess
Owned the rules for what the assistant is allowed to infer versus what it must never guess, and governance around high-risk fields, including traceability between bot-inferred and human-stated values. A mandatory human-approval step gates every send; the assistant's job ends at "task set up and submitted."
Scope & requirements
Deciding what "done" means
Sole PM defining scope, requirements, and exit conditions on a team with no designer and no QA. Work ships in small slices, each with an agreed bar for when it's good enough to move on rather than a judgement call made in the moment.
Alignment
Framing trade-offs for leadership
Surfaced foundational gaps mid-build and drove them to locked decisions, and took roadmap, risks, and open trade-offs to leadership as options with explicit pros and cons rather than pre-baked recommendations.
Ways of working
A waterfall-free model, and the process to keep it honest

With one engineer and me, we co-designed a deliberately lean operating model. No PRDs, no tech-design cycle, no tickets, no sprints. Direction is set at kickoff, and detail gets worked out while building through a daily plan → build → test loop. In place of formal docs we keep two lightweight shared artifacts: a living requirements doc that captures the conversation paths and the product logic the model may never guess, and an improvement log where bugs and enhancements are prioritised and closed (engineer marks a fix done, PM verifies before it closes, preserving a quality gate without a QA function).

Speed is the point of the model, but I stay explicit about its trade-offs: more AI-generated output than two people can fully review, and little record of why a decision was made. So the process I built is aimed squarely at those two risks, capturing decisions and their rationale as we go, and agreeing up front what "done enough" means for each slice.

Where it's at
First phase, in internal testing

The first phase proves the conversational model end-to-end on the simplest notification type, covering both single-task and batch (mass) creation, with more phases planned from there. I planned and ran the project's first live internal test with a regional PM, which surfaced a critical bug and validated real demand for creating tasks in bulk, both of which fed straight back into sequencing discussions.

It's still early and still in build. This page stays intentionally high level because the product is internal; I'll add more as it matures.
